Upscale model speed benchmark

One tile through the model, timed. Speed only — nothing here looks at the picture. Each model comes from the notebook of the same name, published into models/ by its own export cell.

ms / run is the fastest sample and median the middle one, where a sample is a whole batch of runs timed together and divided — never one run timed, which finishes under the clock’s resolution. The gap between the two is how noisy the machine is. A run is whatever the graph was exported to take: one tile, a batch of them, or a whole frame.

ns / kept px is that run divided by the output pixels it is worth keeping — the model’s cost with the geometry taken out of it, and the only column two different tile sizes can be compared by. Frames per second is deliberately not a column: a run is a tile, so a rate of runs says more about the step a graph was exported at than about the model in it, and a 256 step is worth four times a 128 step before either has been run. ns / frame px is the same number with the geometry put back: what a 1920×1080 output costs per pixel of it, including everything the tiling computes past its edge and every halo it computes twice. The two are equal only for a geometry that tiles the frame exactly, and their ratio is what the tiling is wasting. runs / frame and 1080p frame follow from that, the second assuming every run costs the same and that nothing happens between them — a floor, not a frame rate. Multiply ns / frame px by the pixels of any other output to get its floor: 2.07 M for 1080p, 8.29 M for 4K.

Backend is stated, never chosen for you, and a backend that cannot run the model fails the run instead of quietly substituting another — two rows produced by two different runtimes are not a comparison. Only WebGPU can hold tensors in GPU memory or record a command buffer, so WebGL and WASM always read as a CPU round trip with plain runs, and only WebGPU can report a GPU time. Changing it settles the Model selection by asking that backend: it runs each model once, cheapest first, until one goes through, and that one is selected. A refusal costs almost nothing — the runtime throws on the first dispatch of the operator it lacks, in single milliseconds against tens or hundreds for a run that works — so the walk is paid for by the model it stops on, whose session the first benchmark then reuses as its warmup. Every model refused along the way is disabled in the list with the runtime’s own words on it. Nothing is predicted: a model nothing has asked about yet stays selectable, and fails with ORT’s message if it cannot run, which is then remembered too. WebGL additionally has float32 tensors only, and its operator coverage is partial — a graph it cannot run says so, naming the operator.

GPU is the model itself, summed from WebGPU timestamp queries written either side of each kernel, and dispatch is everything the wall clock adds around it. They are separate because a clock around run() cannot see below one queue.submit(), which ONNX Runtime issues once per run whatever the graph does — so any model cheaper than that submit reports the submit instead of itself, and a single Resize over 0.2 MPixel is cheaper than it by an order of magnitude. Read GPU to compare models and dispatch to see what tiling costs you: a client running 40 tiles a frame pays it 40 times. Blank where the adapter cannot time its own kernels.

Data is where the tile lives while the model runs. GPU-resident uploads it once and leaves the result in GPU memory, so the number is the model. CPU round trip hands the runtime a JS array and reads the result back every run — 209 KB up and 836 KB down through a queue fence for a 132 tile, the same cost whatever the graph does. Run the two back to back and the difference is the copy: it is large enough to make a one-node Resize and a convolution stack report the same time, which is a measurement of the bus, not of the models.
